01Qué cambia según la respuesta

Esto es investigación con decisión detrás, no lectura: cada resultado mueve una apuesta concreta.

  • Si el estándar oficial basta → no se toca nada: GitHub ya genera el TOC, la checklist de comunidad y los health files. Solo se rellenan huecos [3].
  • Si el ecosistema exige más (standard-readme, READMEs curados) → se adopta una plantilla única y se reescriben los READMEs propios, empezando por los peores [8][9].
  • Si el perfil es la pieza crítica → el repo donde estamos (soydachi/soydachi, 1.325 bytes, health 28 %) es la portada: estructura, banner claro/oscuro y fixes de accesibilidad [5][12].
  • Si las imágenes importan → el par de banners ya existe, generado con la guideline de soydachi.com (papel cálido + bloque ámbar, un solo material oscuro) [14][15].

Resultado de esta corrida: ambas. La fuente oficial cubre el piso (§03), el ecosistema marca el techo (§04), y la auditoría (§05–06) dice exactamente dónde está el hueco. La propuesta cierra en §07–09 y las tres direcciones en §12.

03Qué dice la fuente primaria (GitHub)

La documentación propia de GitHub es la única voz normativa; el resto es estilo [1].

README mínimo

Cinco preguntas: qué hace el proyecto, por qué es útil, cómo empezar dónde pedir ayuda, quién lo mantiene. Junto al README: licencia, CONTRIBUTING y code of conduct comunican expectativas [1][2].

docs.github.com · about-readmes · best-practices-for-repositories

Ubicación y TOC

.github/, raíz o docs/ (en ese orden de precedencia); trunca a partir de 500 KiB. El TOC se genera solo con el menú Outline; no hay que escribirlo a mano en GitHub [1].

docs.github.com · about-readmes

Community profile

La checklist mide README, LICENSE, CODE_OF_CONDUCT, CONTRIBUTING, SECURITY, issue/PR templates. Es lo que devuelve el health_percentage de la API [3].

docs.github.com · community-profiles

Health files por defecto

Un repo .github público por cuenta u organización provee CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, SUPPORT y templates a todos los repos que no tengan los suyos. Una sola carpeta, todo el alcance [4].

docs.github.com · creating-a-default-community-health-file

README de perfil

Repositorio público con el nombre del usuario + README.md en la raíz. Nada más. Se muestra sobre los pinned repos [5].

docs.github.com · managing-your-profile-readme

Enlaces relativos

Los enlaces e imágenes relativos sobreviven a cambios de rama y clonados; GitHub los reescribe siempre. Absolutos a blob/<rama>/ se rompen cuando la rama muere [1].

docs.github.com · about-readmes

Accesibilidad del perfil — el post propio de GitHub

Cinco reglas: enlaces descriptivos (nada de "aquí"), alt de imagen como tweet (sucinto y con contexto), estructura de encabezados sin saltos de nivel, lenguaje plano, y emoji con mesura (el lector de pantalla los deletrea) [6]. El README de perfil actual no tiene ni un # [12].

Lo que la investigación profunda añade

NotebookLM sintetizó 65 fuentes el 2026-09-28 [11]:

  • Anatomía de 9 secciones para README de proyecto: identidad + badges dinámicos (CI, cobertura, versión, licencia), demo visual, TOC, quickstart, uso/API, contributing, seguridad/soporte, licencia.
  • Perfil en 3 niveles: identidad → telemetría viva (stats/actividad) → proof-of-work (proyectos reales enlazados, no contadores de vanidad).
  • 5 pitfalls medidos en las fuentes: saturación de badges y caída de proveedores nicho; alt genérico; #gh-dark-mode-only descontinuado (rompe en visores externos — usar <picture>); link-rot por rutas absolutas a ramas; ejemplos de código desactualizados.

Ejemplo mínimo de libro: vuejs/core — título con 3 badges, "Getting Started" que apunta a la doc,Issues/Contribution/License. Un README corto también es profesional [13].

07Plantilla propuesta — README de proyecto

Orden combinado de la especificación y la fuente oficial. Para los 15 repos propios; los 6 forks quedan fuera [8][1].

plantilla-proyecto.md 
<h1 align="center">Nombre</h1>
<p align="center">una frase <120 caracteres, igual a la descripción del repo</p>
<!-- badges: 3–6, alt descriptivo, vía <picture> si el logo cambia de tema -->

## Instalación      // comandos exactos, con prerequisitos y versiones
## Uso             // quickstart copy-pasteable + 1 ejemplo real
## Configuración   // solo si existe
## Contribuir      // enlaza CONTRIBUTING.md / issues (o el default de .github)
## Seguridad       // enlaza SECURITY.md
## Licencia        // SPDX, última sección, siempre
  • TOC manual: solo si el README supera ~150 líneas o se lee fuera de GitHub — en GitHub el Outline ya lo trae [1]. Ver §10.
  • Badges: 3–6 de alta señal (CI, versión, licencia, descargas). Los curados abusan; la guía práctica recomienda contenerse [9][17].
  • El referente ya está en casa: arcasilesgroup/ai-engineering (hero + badges adaptativos + tabla de cifras + tour) es el nivel a copiar [16].
  • Health files: no los dupliques — crea el .github de cuenta y que GitHub los aplique donde falten [4].
